# 12. Supply chain — what you install on the box

Every previous section is about who can reach your server. This one is about what you invite in yourself. A hardened box with a default-deny firewall and key-only SSH is still fully compromised the moment you run `pip install` on a package that executes someone else's code during installation — as root, in the same shell that has your keys.

The uncomfortable part: this is the one attack path where the operator does all the work for the attacker.

---

## 12.1 Install-time code execution

**The failure.** Installing from a source distribution runs its build script. In Python that is `setup.py`, executed on your machine with your privileges before you have imported anything. In Node the equivalent is a `postinstall` hook in `package.json`. Neither requires you to *use* the library: the code runs at install time, and it runs as whoever ran the installer.

**The fix.** Refuse source distributions and pin the version:

```bash
# Python — wheels only, exact version
pip install --only-binary=:all: requests==2.32.3

# Node — skip lifecycle scripts for a dependency you don't trust yet
npm install --ignore-scripts some-package@1.4.2
```

`--only-binary=:all:` makes pip fail rather than fall back to a source build, which is the point: a package that can only be installed by executing its own build script is a decision, not a default.

**Why not make it global.** Putting `only-binary` in `pip.conf` for every project sounds tidy and breaks quietly — plenty of legitimate packages ship no wheel for your platform, and the failure looks like a broken environment rather than a policy. Apply it per command, deliberately.

**Verify.**

```bash
# Did anything arrive as a source build?
pip download --only-binary=:all: -d /tmp/whl <package>==<version> && echo "wheel available"

# What lifecycle scripts would a node install run?
npm install --dry-run --foreground-scripts 2>&1 | grep -i -E 'postinstall|preinstall'
```

## 12.2 The package name is a claim, not a fact

**The failure.** A plausible-looking package name is not evidence that the package is the one you mean. Two ways this goes wrong:

- **Typosquatting** — a name one character away from the popular one.
- **Slopsquatting** — an LLM suggests a package that does not exist, someone registers that exact name, and the next person who follows the same suggestion installs it. The name *sounds* canonical because a model generated it, which is precisely why it gets typed without checking.

Copy-pasting an install command out of a chat, a blog post, or a README is the delivery mechanism in both cases.

**The fix.** Before installing anything you have not used before, spend fifteen seconds on provenance: who publishes it, when it first appeared, how much it is actually used. A package registered three weeks ago under a familiar-sounding name is a red flag, not a lucky find.

```bash
# Python
pip index versions <package>                    # does it exist, what versions
curl -s https://pypi.org/pypi/<package>/json | python3 -c \
  'import json,sys; d=json.load(sys.stdin)["info"]; print(d["author"], d["home_page"], d["project_urls"])'

# Node — first publish date and maintainers
npm view <package> time.created maintainers versions --json | head -20
```

**Verify.** The install you are about to run names an *exact* version that you looked up, from a publisher you recognized, on a project that existed before this week.

**What will not save you.** A vulnerability scanner (`pip-audit`, `npm audit`) checks published advisories. Malware uploaded this morning is not in an advisory database yet — audit tools are for known-bad, not for new-bad. Treat a clean audit as "nothing known against it", not as "safe".

## 12.3 The package that behaved for a year

**The failure.** A dependency is fine for a long time, then a maintainer account is compromised or handed over, and a few lines arrive in a patch release. If your install resolves to "latest", you adopt those lines the next time you deploy — silently, on a box you consider hardened.

**The fix.** Pin exact versions and commit the lock file. Update as a deliberate act, not as a side effect of a rebuild.

```bash
pip install -r requirements.txt   # every line ==pinned, generated by pip freeze
npm ci                            # honors package-lock.json exactly; npm install may not
```

**Verify.**

```bash
# Anything unpinned in the requirements the server actually installs?
grep -vE '==|^#|^$' requirements.txt && echo "^ unpinned lines above"

# Ranges left in production dependencies?
grep -E '"\^|"~' package.json
```

## 12.4 `curl | bash`

**The failure.** Piping a remote script straight into a shell means the code that runs is whatever the server decided to send at that moment, unread, at your privilege level. It is also trivially conditional: a server can serve a clean script to a browser and a different one to `curl`.

**The fix.** Two steps instead of one — download, read, then run:

```bash
curl -fsSL https://example.com/install.sh -o /tmp/install.sh
less /tmp/install.sh          # actually read it: what does it write, what does it fetch, does it need root
bash /tmp/install.sh
```

Where the project publishes a checksum or a signature, check it before reading. Where it publishes neither, note that this is the level of assurance you are getting.

**Verify.** `grep -nE 'curl|wget|sudo|/etc/|~/\.' /tmp/install.sh` — the interesting lines are the ones that fetch more code, escalate, or write outside the install prefix.

## 12.5 Don't install into the system as root

**The failure.** Packages installed globally as root put third-party install-time code, and every later upgrade of it, in the most privileged context on the box. It also makes two projects share one dependency set, so an upgrade for one silently changes the other.

**The fix.** A virtualenv (or a per-service user) for each service, and no `sudo pip`:

```bash
python3 -m venv /opt/<service>/.venv
/opt/<service>/.venv/bin/pip install --only-binary=:all: -r requirements.txt
# service runs as its own unprivileged user, owning only its own directory
```

**Verify.**

```bash
ls -ld /opt/*/.venv                      # each service has its own environment
systemctl show <service> -p User         # not root
pip list --user 2>/dev/null | head       # nothing important living in a root-global set
```

---

## The one lesson

Reachability is what an attacker exploits; **installation is what you hand over voluntarily.** The same discipline that applies to opening a port applies to adding a dependency: name what you are letting in, name the version, and know what it runs at the moment you let it in.
